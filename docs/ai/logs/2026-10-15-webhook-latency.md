  - 측정용 댓글이 스터디원이 보는 실제 질문 글에 남음. 사람이 삭제해야 함

## 후속: 수정·삭제 후 새로고침 지연과 열린 화면 반영

- 사람의 관찰: "추가는 빠른데 수정·삭제는 새로고침해야 반영되고, 새로고침에 약간 딜레이가 있다"
- 확인(추측하지 않고 측정):
  - GitHub 웹훅 전달 기록(`gh api repos/.../hooks/{id}/deliveries`): 삭제 이벤트 3건 모두 응답 200, 0.05~0.36초. 웹훅은 정상
  - 삭제는 이미 사이트에 반영돼 있었음(사이트와 GitHub 모두 댓글 2개)
  - 로컬에서 실제 GitHub 데이터로 재현: 웹훅 직후 첫 방문 2.65~2.91초, 이후 2ms. 원인은 `expire: 0`으로 즉시 비운 뒤 첫 방문자가 GitHub 조회를 기다리는 구조(내가 고른 설계의 부작용)
  - "열린 화면은 새로고침해야 수정·삭제가 반영"은 스펙에 적힌 대로의 동작이었음
- 사람이 정한 것: 열린 화면도 수정·삭제를 자동 반영(수정됨 표시, 삭제는 제거)
- 구현: 웹훅 응답 후 캐시 미리 채우기(변경 확인과 재시도 포함), 열린 화면 폴링에서 수정·삭제 반영
- 확인 결과: 테스트 99개 통과. 웹훅 직후 1.5초 뒤 방문 6~11ms(이전 2.65~2.91초). 폴링 E2E 15건 통과(수정 반영 15.1초, 삭제 카드 제거, 알림 "수정 1건, 삭제 1건이 반영되었습니다.", 위쪽 변경에도 보던 카드 446 → 447px). 웹훅 E2E 14건 통과
- 확인 못함: 운영(Vercel)에서의 미리 채우기 효과(`after`가 서버리스에서 끝까지 도는지, `maxDuration` 30초 적용), 변경 확인 로직이 실제 GitHub 지연 상황에서 재시도하는 경로(단위 테스트로만 확인)
- 틀렸거나 아쉬웠던 점:
  - 처음 설계에서 "첫 방문자가 조회를 기다린다"는 비용을 ADR-0001에 적지 않았음. `expire: 0`을 고른 이유(옛 내용 방지)만 적고 대가를 빠뜨림
  - 폴링 E2E 수정·삭제 항목이 처음 한 번 실패: 기준 카드가 하필 삭제한 카드였음. 제품 문제가 아니라 시나리오 문제여서 "화면 위쪽 변경이 보던 카드를 밀지 않는가"로 기준을 바꿈
  - 병합 함수에 쓸모없는 빈 함수(`clearUnlessMarked`)를 남겼다가 직접 발견해 삭제
  - 문서에 절 번호를 6.0, 6.2, 6.1 순서로 넣어 꼬였다가 정리
