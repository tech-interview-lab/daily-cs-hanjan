# ADR-0001 렌더링 방식 선택

| 항목 | 내용 |
|---|---|
| 상태 | 확정 (2026-10-15) |
| 작성일 | 2026-10-15 |
| 관련 요구사항 | FR-4, C-4, C-5 |
| 영향 범위 | `site/src/main`, `site/src/app`(Next.js 라우트), 배포 설정. 상세는 [site-structure.md](../site/site-structure.md) 10~11장 |

## 1. 맥락

새 댓글은 등록 후 1분 이내 사이트에 반영되어야 합니다(FR-4). 운영 비용은 추가로 발생하지 않아야 하며(C-5), 기존 EC2 서버는 사용할 수 있습니다(C-4). 사이트는 읽기 전용이므로 쓰기 경로가 없습니다. 데이터의 원본은 GitHub Discussions입니다.

요구사항 제공자가 아래 두 가지를 추가로 정했습니다.

- 새 댓글이 달리면 사이트 전체가 아니라 해당 질문 부분만 갱신합니다.
- 반영은 1분 이내를 넘어 거의 즉시를 목표로 합니다.

## 3. 선택지

| 안 | 반영 경로 | 장점 | 단점 및 위험 |
|---|---|---|---|
| A. 정적 사이트 + 이벤트 재빌드 | 댓글 이벤트 → Actions 빌드 → Pages 배포 | 서버 불필요 | 댓글 하나에도 전체 재빌드. 부분 갱신 불가 |
| B. 요청 시 재검증(Next.js) | 웹훅 → 해당 질문 캐시만 무효화 → 다음 요청에서 그 질문만 다시 조회 | 부분 갱신. 반영 지연은 웹훅 전달 시간 수준 | Node 실행 환경 필요 |
| C. 요청 시 SSR(캐시 없음) | 요청마다 GraphQL 조회 | 항상 최신 | 요청마다 외부 API 호출. 호출 한도와 지연 |
| D. CSR | 브라우저가 직접 조회 | 서버 로직 최소 | 브라우저에 토큰 노출. 별도 안으로 보지 않음 |
| E. EC2 웹훅 + 증분 갱신 | 웹훅 수신 → 해당 질문만 갱신 → nginx가 정적 파일 제공 | 부분 갱신 | 증분 갱신 로직과 서버 운영을 직접 구현. EC2 장애가 곧 사이트 장애 |

## 5. 반영 경로

| 단계 | 동작 |
|---|---|
| 1 | 댓글 등록 → GitHub가 `discussion_comment` 웹훅을 Vercel의 수신 경로로 전송 |
| 2 | 웹훅 서명(`X-Hub-Signature-256`) 검증. 실패 시 401 |
| 3 | 해당 질문 태그(`q-{number}`)와 목록 태그(홈, 카테고리, 작성자, 검색에 쓰는 전체 목록) 재검증 |
| 4 | 웹훅 응답 직후(`after`, `maxDuration` 30초) 그 질문과 목록을 미리 조회해 캐시를 채움. 웹훅이 알려 준 변경이 조회 결과에 아직 없으면 낡은 항목을 비우고 최대 3회 재시도, 끝내 안 되면 비운 채 둠 |
| 5 | 이후 방문은 캐시를 받음. 미리 채우기가 끝나기 전에 온 방문은 그 조회를 함께 기다림 |
| 6 | 이미 질문 상세를 연 화면은 15초 폴링으로 추가, 수정, 삭제를 받아 답변 목록만 다시 그림([site-design.md](../site/site-design.md) 5.3) |

- 웹훅 누락 대비로 시간 기반 재검증을 함께 둡니다. `cacheLife("hours")`로 1시간마다 다시 확인합니다(S1 적용).
- 미리 채우기를 둔 이유: `expire: 0`은 변경 뒤 첫 방문자가 GitHub 조회(로컬 실측 2.6~2.9초)를 직접 기다리게 합니다. 운영에서 수정·삭제 후 새로고침이 느리다는 관찰로 확인했고, 응답 후 미리 채우면 웹훅 도착 약 3초 뒤부터는 누가 방문해도 6~17ms입니다(6.2).
- 확인 로직을 둔 이유: 웹훅 직후 GitHub 조회가 변경을 아직 담지 않으면 옛 데이터가 1시간 캐시에 남을 수 있습니다. 웹훅 본문의 댓글 ID와 수정 본문으로 "정말 바뀐 상태인지" 확인합니다.
- 재검증은 `revalidateTag(tag, { expire: 0 })`을 씁니다. 권장값 `"max"`는 무효화 직후 방문자에게 옛 내용을 한 번 더 보여 줘서 "거의 즉시 반영"과 맞지 않습니다(Next.js 16 문서 확인).
- 질문 생성 파이프라인이 새 질문을 올리거나 이전 질문을 닫을 때는 `discussion` 웹훅으로 같은 경로를 탑니다.

## 6. 검증

결정을 위한 실측은 필요 없어졌고, 아래 항목은 구현 후 동작 확인용입니다.

| 항목 | 방법 | 기준 |
|---|---|---|
| 반영 지연 | 테스트 댓글 `createdAt`부터 공개 URL에서 댓글이 보이는 시각까지 1초 간격 조회, 3회 | 중앙값 60초 이내(FR-4) |
| 열린 화면 반영 | 질문 상세를 연 채 테스트 댓글 등록 | 폴링 주기 안에 목록 끝에 추가 |
| 부분 갱신 | 재검증 후 다른 질문 페이지의 응답이 캐시에서 제공되는지 확인 | 해당 질문과 목록만 다시 조회 |
| 서명 검증 | 잘못된 서명으로 웹훅 전송 | 401, 재검증 없음 |

### 6.0 운영 반영 지연 실측 (2026-10-15, Vercel Hobby)

`site/scripts/measure-latency.mjs`로 운영 주소의 `/q/34`를 일반 방문자와 같은 요청(캐시 우회 없음)으로 1초마다 조회했습니다. 측정 구간은 GitHub이 기록한 댓글 `createdAt`부터 그 댓글이 응답 HTML에 나타난 시각까지입니다.

| 시도 | 댓글 등록(createdAt) | 사이트 노출 | 소요 시간 | 시계 보정 후 | `x-vercel-cache` |
|---|---|---|---|---|---|
| 1 | 04:48:23Z | 04:48:28.114Z | 5.11초 | 4.49초 | REVALIDATED |
| 2 | 04:48:49Z | 04:48:54.829Z | 5.83초 | 5.21초 | REVALIDATED |
| 3 | 04:49:08Z | 04:49:13.235Z | 5.24초 | 4.61초 | REVALIDATED |

- 중앙값 5.24초(보정 후 4.61초), 최댓값 5.83초. 판정 기준(중앙값 60초 이내)을 충족합니다. **FR-4 충족.**
- 시계 보정은 측정 컴퓨터와 GitHub 서버 시계의 차이(초 해상도로 +0.62초)를 뺀 값입니다. `createdAt`이 초 단위로 잘려 있어 실제 값은 표의 값보다 최대 1초 짧을 수 있습니다.
- 한계: 표본 3건, 질문 1개, 한 시간대 측정입니다. 웹훅 전달 시간이 GitHub 쪽 부하에 따라 달라질 수 있습니다. 폴링으로 열려 있는 화면에 붙는 시간은 위 값에 최대 15초가 더해집니다.
- 이 측정으로 ADR-0001의 남은 확인 항목(반영 지연) 중 운영 환경 확인이 끝났습니다. 부분 갱신, 서명 검증은 6.1의 로컬 검증을 따릅니다.

### 6.1 S2 로컬 검증 결과

`site/scripts/e2e-webhook.mjs`(fixture 데이터, `next start`)로 14건 모두 통과했습니다. 원문은 `docs/ai/logs/2026-10-15-s2-question-detail.md`에 있습니다.

- 웹훅 직후 첫 요청에서 새 답변 표시(로컬 109ms). 웹훅 전에는 캐시된 옛 내용 유지
- 서명이 틀린 웹훅은 401이고 재검증 없음
- 새 질문과 삭제된 질문도 반영(새 질문 200, 삭제 404)
- 부분 갱신: 101번 웹훅으로는 102번 데이터를 다시 가져오지 않음

배포 직후에는 각 페이지가 처음 다시 그려질 때 데이터를 한 번 새로 조회합니다(운영에서는 위 6.0의 실측으로 동작을 확인했습니다). 빌드 때 만든 캐시 항목이 실행 중인 서버의 메모리 캐시에 없기 때문입니다. 그 뒤로는 질문 단위로만 갱신됩니다. 정확성에는 영향이 없고 배포마다 GitHub 호출이 조금 늘어납니다. Vercel의 캐시 동작은 로컬과 다를 수 있어 운영 확인이 필요합니다.

### 6.2 변경 직후 첫 방문 지연 (2026-10-15)

운영에서 "추가는 빠른데 수정·삭제 후 새로고침이 약간 느리다"는 관찰이 있었습니다. 웹훅 전달 기록(Recent Deliveries)에서 삭제 이벤트 3건 모두 응답 200, 0.05~0.36초로 정상이었고, 원인은 캐시를 즉시 비운 뒤 첫 방문자가 GitHub 조회를 기다리는 구조였습니다. 로컬(실제 GitHub 데이터)에서 재현해 `site/scripts/measure-first-visit.mjs`로 비교했습니다.

| 웹훅 응답 후 방문 시점 | 미리 채우기 전 | 미리 채우기 후(3회) |
|---|---|---|
| 즉시(0초) | 2.65~2.91초 | 2.79, 2.99, 3.58초 |
| 1.5초 뒤 | 2.65~2.91초(첫 방문) | 11, 10, 6ms |
| 4초 뒤 | 2ms | 9, 4, 7ms |
| 8초 뒤 | 2ms | 17, 12, 6ms |

- 웹훅 도착 약 3초 뒤부터는 지연이 없습니다. 도착 직후 3초 안의 방문은 미리 채우기와 같은 GitHub 조회를 기다리므로 남은 시간만큼 걸립니다(GitHub 조회 자체의 시간이라 줄일 수 없음).
- 운영에서의 재측정은 사용자가 수정·삭제를 해 본 뒤 확인합니다(미확인).
